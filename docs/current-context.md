## What Phonon2D is

A C++ GDExtension that brings physically modelled sound propagation to 2D Godot games and exposes it as a gameplay mechanic. Sound is simulated as discrete energy packets ("phonons") cast from a source. They travel through the scene, reflect off surfaces, get absorbed or scattered depending on material properties, and lose energy over distance. Supports top-down and side-scrolling perspectives.

Planned library pieces:

- **PhononPacket**: lightweight data object. Carries position, direction, intensity, frequency, bounce count, distance travelled. Pooled and recycled when energy drops below a cull threshold. (Direction, not velocity: speed is a property of the medium. Wavelength is derivable so not stored.)
- **PhononEmitter2D**: inherits `AudioStreamPlayer2D`. Emits a configurable number of phonons with frequency, volume, and spread (omni, cone, beam).
- **PhononListener2D**: one per scene. Converts arriving phonons into the audio the player hears.
- **PhononSensor2D**: gameplay node. Evaluates arriving phonons against conditions (intensity threshold, frequency range, hit count, time window) and emits Godot signals. This is what turns sound into a game mechanic (doors, switches, shattering glass, alerting enemies).
- **PhononReceiver**: shared abstraction for listener and sensor with a concrete `receive_packet(packet)`, so the server dispatches to one list of receivers.
- **PhononMaterial**: resource applied to collision bodies, sprites, tilemaps. Absorption coefficient, scattering factor, reflection multiplier. Presets via a `PhononMaterialType` enum (NONE/concrete-like default, FOAM, VELVET, DRYWALL, POLISHED_HARDWOOD, GLASS, PAPER).
- **PhononServer**: singleton that owns the packet pool, advances packets each tick, resolves collisions, dispatches to receivers. Holds medium properties (speed of sound, global attenuation rate) and the cull threshold.

Design principles already settled: material variation is handled with data (coefficients and enums), not interface hierarchies. Marker interfaces with no real behaviour were cut. Every design decision needs to be defensible in a viva, so prefer the simplest approach that can be justified.

## Setup problems already solved (don't re-diagnose these)

1. **g++ failed silently from PowerShell** (exit code 1, no error text, even on a one-line program). In the SCons output this showed up as empty `=====` blocks and every file failing instantly.
   - Cause: something earlier on the Windows PATH shadows DLLs that MinGW's compiler needs. g++ works fine inside the MSYS2 UCRT64 terminal.
   - Fix: put `C:\msys64\ucrt64\bin` at the front of PATH. Per session: `$env:PATH = "C:\msys64\ucrt64\bin;" + $env:PATH`.
   - **Possibly still pending**: making this permanent by adding `C:\msys64\ucrt64\bin` to the top of the **System** Path variable. If a build fails silently in a new terminal, this is why. Check with `g++ t.cpp -o t.exe; echo $LASTEXITCODE` on a trivial file.
   - The offending DLL was never identified. To find it: `where.exe zlib1.dll libwinpthread-1.dll libstdc++-6.dll libgcc_s_seh-1.dll libzstd.dll libgmp-10.dll libiconv-2.dll libintl-8.dll` and look for hits outside `C:\msys64\ucrt64\bin`.

2. **MSYS2 was out of date.** Upgraded with `pacman -Syu` (gcc went from 15.2.0 to 16.2.0). The mirror returned HTTP 429 a few times. Rerunning the command resumes from the cache.

3. **"Linking Static Library" took about 20 minutes** on the first build. With MinGW, godot-cpp archives its 1000+ object files slowly, and Windows Defender makes it worse. It's a one-off. Later builds only recompile files in `src/`. Adding `C:\MyStuff\Projects` as a Defender exclusion speeds things up.

4. **godot-cpp versioning.** The docs still say to use the godot-cpp branch matching your Godot version, but branches stop at 4.5. Since v10, godot-cpp is versioned independently and targets a Godot version through the `api_version` build option. The template pins a godot-cpp commit as a submodule, so nothing needs choosing.

## PinkCircle (history: first custom node, still in `src/` as a placeholder)

Goal: add a `PinkCircle` node extending `Node2D` that draws a pink circle, with an exported `radius` property. Small on purpose. It exercises exactly what Phonon2D will need: class registration, an exported property, `_process`, and `_draw`.

`src/pink_circle.h`

```cpp
#pragma once

#include <godot_cpp/classes/node2d.hpp>

using namespace godot;

class PinkCircle : public Node2D {
	GDCLASS(PinkCircle, Node2D)

	float radius = 50.0f;
	double time = 0.0;

protected:
	static void _bind_methods();

public:
	void set_radius(float p_radius);
	float get_radius() const;

	void _process(double delta) override;
	void _draw() override;
};
```

`src/pink_circle.cpp`

```cpp
#include "pink_circle.h"

#include <godot_cpp/core/class_db.hpp>
#include <godot_cpp/core/math.hpp>

void PinkCircle::_bind_methods() {
	ClassDB::bind_method(D_METHOD("set_radius", "radius"), &PinkCircle::set_radius);
	ClassDB::bind_method(D_METHOD("get_radius"), &PinkCircle::get_radius);
	ADD_PROPERTY(PropertyInfo(Variant::FLOAT, "radius"), "set_radius", "get_radius");
}

void PinkCircle::set_radius(float p_radius) {
	radius = p_radius;
	queue_redraw();
}

float PinkCircle::get_radius() const {
	return radius;
}

void PinkCircle::_process(double delta) {
	time += delta;
	queue_redraw();
}

void PinkCircle::_draw() {
	float r = radius * (1.0f + 0.2f * (float)Math::sin(time * 3.0));
	draw_circle(Vector2(), r, Color(1.0f, 0.4f, 0.7f));
}
```

`src/register_types.cpp`: add `#include "pink_circle.h"` and `GDREGISTER_CLASS(PinkCircle);` (already done).

Lesson from it: GDExtension nodes run `_process` inside the editor too, not only in the running game. Phonon2D will need to guard against that (`Engine::get_singleton()->is_editor_hint()`) so the simulation doesn't tick while editing scenes.
